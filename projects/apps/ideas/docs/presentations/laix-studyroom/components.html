Decision logic 01 / 07Decisions

Core · decision logic

Decisions

The input and the answer. The host sends a DecisionRequest; LAIX returns a Decision with verb, action, confidence, alternatives, constraints, approval and audit.

What it contains

  • DecisionRequest — what the host sends: situation, signals, options or attributes
  • Situation — observations and beliefs the host supplies
  • Decision — what LAIX returns: verb, action, alternatives, constraints and basis()
  • Breakdown, evidence ref, intent and escalation helpers

What it touches

  • Every rule set returns the Decision shape
  • The host maps the Decision to its own action model
  • The record layer keeps it

Why it matters

A score ranks inside one rule set. Confidence is not a probability unless calibrated says so. Alternatives and constraints make the answer explainable.

laix/core/decisions.py“This is not a prompt and a reply. It is a decision with a receipt.”
Decision logic / Decisions01
Point at the fields: verb, action_id, score, confidence, confidence_source, calibrated, alternatives, constraints_applied, requires_approval. The host uses these fields; it does not parse prose.
Inside DecisionsBelief

Concept · not a separate component

Belief: what the host thinks.

A Belief is a proposition with a confidence and its evidence. It is not a fact and not a decision. The host puts beliefs into the Situation; a policy scores against them.

The record

  • Belief(id, proposition, confidence)
  • Evidence, source and updated time
  • Confidence is 0..1

The meaning

  • “learner may need help” at 0.56
  • “socket is live” at 0.90
  • A belief is what the host currently thinks, not proof

The use

  • A Situation holds beliefs
  • A policy scores against them
  • The record keeps the evidence and its source
ExampleHOST PROVIDES Belief(id="b1", proposition="learner may need help", confidence=.56, source="host-fusion")LAIX USES Situation(beliefs=(b1,), constraints=...)
Inside Decisions / Belief01a
Belief is not a 17th component. It is a core request record. The host supplies a proposition, a confidence and its evidence; LAIX treats it as a belief, not a fact. This is the record the Perception slide produces as Belief(“may need help”).
Decision logic 02 / 07Policies

Core · decision logic

Policies

The rule sets. A policy reads a request and returns a decision. Some policies are built in; eight packaged policies cover common decision classes; a custom policy carries the domain rules.

What it contains

  • Built-in policies for the two request shapes
  • Eight packaged policies for common decision classes
  • Registry, custom policy protocol and bandit policy

What it touches

  • Decisions and the host
  • The host selects one active policy
  • Tests prove the behaviour

Why it matters

One active policy at a time. The host can replace a policy without forking LAIX. The decision shape stays the same.

laix/core/policies/“Domain rules live in the host. The decision mechanics live in LAIX.”
Decision logic / Policies02
One active policy at a time. register_policy stores; use_policy activates. The eight packaged policies are deterministic defaults, not trained models.
Inside PoliciesAction

Concept · not a separate component

Action: what the host can do.

An Action is a candidate option, not a decision and not the verb act. The host offers options, each with a verb; a policy chooses one; the decision returns that option's verb and action_id.

The record

  • Action(id, verb, name) — an option
  • Benefit, risk, delay, cost, interruption
  • Reversible, approval needed, app params

The verb

  • ask and act are both verbs
  • An option can carry wait, guide, ask, act, verify or escalate
  • The decision repeats the chosen option's verb

The policy

  • The built-in action policy lives in Policies
  • It filters hard constraints, then ranks the options
  • It chooses one; the rest become alternatives
ExampleHOST OFFERS 3 OPTIONS• Action(id="ask-ben", verb="ask", risk=.35, requires_approval=True)• Action(id="open-board", verb="act", risk=.52)• Action(id="hint-alice", verb="guide", risk=.05)LAIX RETURNS 1 DECISION• Decision(verb="ask", action_id="ask-ben")
Inside Policies / Action02a
Action is not a 17th component. It is an option record inside the decision request, a verb in the decision, and a built-in policy inside Policies. The host offers options; LAIX chooses one. This bridge exists because readers otherwise see “act” and “action_id” without knowing what an Action is.
Decision logic 03 / 07Attention

Core · decision logic

Attention

Which signal deserves attention now. Severity, timing, quiet hours, dedupe and feedback — separate from the action decision.

What it contains

  • Signal and Context
  • Attention policy, scoring and timing
  • Feedback, outcome log and replay

What it touches

  • Signals, context and decisions
  • The request shape selects attention
  • Host delivery and notification policy

Why it matters

A notification is not automatically worth attention. Quiet hours, severity and history are part of the decision, not an afterthought.

laix/core/attention/“Attention is a decision class, not a notification setting.”
Decision logic / Attention03
Attention answers “should this reach the user now?” It is separate from “what should we do?” The same signal can be high severity and still wait because of quiet hours or dedupe.
Decision logic 04 / 07Outcome learning

Core · decision logic

Outcome learning

What happened after the decision. Labels, attribution and bounded priors — counting, not model training.

What it contains

  • OutcomeLedger and OutcomeStore
  • UCBBandit, arms and reward mapping
  • Labels: helped, neutral, hurt, unknown

What it touches

  • Decision ids and measured results
  • Policy priors
  • Host measurement and attribution

Why it matters

No outcome means no learning. Attribution is the hard part: attach the result to the intervention, not the final check.

laix/core/outcome.py“A decision without an outcome is just an opinion with a timestamp.”
Decision logic / Outcome learning04
This is bounded counting. UCB adds a small prior, not a trained model. The host owns the measurement. StudyRoom’s Phase 0 attribution needs tightening: attach the outcome to the intervention, not the final verify.
Decision logic 05 / 07Evaluation

Core · decision logic

Evaluation

A policy change needs a fixture, not a vibe. Cases, rows and reports compare policies and Python/TypeScript results.

What it contains

  • Case, Row, Report
  • compare() and load_cases()
  • Field-level mismatch reporting and agreement rate

What it touches

  • Policy outputs and shared fixtures
  • Bench suites and their cases
  • Release and upgrade checks

Why it matters

You can change a policy safely only when the expected verb, reason, action and approval are pinned.

laix/core/evaluation.py“If you cannot replay it, you cannot claim it improved.”
Decision logic / Evaluation05
The harness compares selected fields: verb, reason_code, deliver, record, requires_approval. It is not trying to compare prose. Use it for policy changes and Python/TypeScript parity.
Decision logic 06 / 07Perception

Core · decision logic

Perception

The data shapes for what a detector sees. The host supplies detectors; detections become Belief records; LAIX keeps the frame and the decision separate.

What it contains

  • Detector, Detection
  • PerceptionEvent, PerceptionFrame
  • Cheap and deep metadata contracts

What it touches

  • The perception loop and resource budgets
  • Host cameras, STT, sensors and app events
  • Decision requests built from detections

Why it matters

Perception is contract-first. The core does not ship a model or a camera; it defines what the host must provide.

laix/core/perception.py“The host sees. LAIX defines what a useful observation looks like.”
Decision logic / Perception06
Perception is the bridge from raw host events to structured observations. The detector implementation stays in the host. The core only owns the contract and frame shape.
Decision logic 07 / 07Resources

Core · decision logic

Resources

Which sensing or model call is worth making. Cheap runs continuously; deep runs only when gain, uncertainty, cost and latency justify it.

What it contains

  • Budget, SensingOption
  • ResourcePlan and ResourcePolicy
  • Allowed and skipped reasons

What it touches

  • Perception and the detection loop
  • Host compute and model budget
  • Outcome and cost metrics

Why it matters

Unlimited deep calls are how a live system becomes slow and expensive. The plan records what was skipped and why.

laix/core/resources.py“Spend the expensive look where uncertainty is high and the answer matters.”
Decision logic / Resources07
The resource policy is deterministic. Cheap detectors are admitted. Deep calls must clear information gain, cost and latency budgets. The skipped list is the evidence that the system was disciplined.
Integration 01 / 07Layer

App kit · integration

Layer

The one object a host calls. It routes the request to the attention policy, the action policy or a selected policy, and returns the public decision.

What it contains

  • Layer, DecisionRequest, Decision
  • Policy registry and active policy
  • Built-in request routing

What it touches

  • Core policies and decisions
  • App-kit runtime and records
  • Every host integration

Why it matters

One public entry point keeps the integration small. The host does not need to know which policy class runs behind it.

laix/appkit/layer.py“One request in, one decision out. That is the whole host surface.”
Integration / Layer08
Layer is optional in the sense that a host can use core policies directly, but it is the public convenience surface. It has one active policy at a time. The request shape selects attention or action when no policy is set.
Integration 02 / 07Runtime

App kit · integration

Runtime

The wiring around a decision: observe, state, policy, execution, outcome. Every decision gets a trace; every execution gets a receipt.

What it contains

  • DecisionRuntime, ExecutionBridge
  • ExperienceState, StateStore
  • ApprovalRequired, UnknownAction and traces

What it touches

  • Policies, resources and outcomes
  • Host execution and state ports
  • Host task and execution

Why it matters

The runtime is in-process and dependency-free. A cloud service can persist the same records later.

laix/appkit/runtime/“The runtime wires the pieces. The host still owns the task.”
Integration / Runtime09
DecisionRuntime is the convenience wiring: observe, decide, execute, outcome. It is not a hosted service. The host can use it or call Layer directly. The task lifecycle and execution authority still belong to the host.
Integration 03 / 07Records

App kit · integration

Records

What happened, why, who approved, and whether it can be undone. The record is the audit surface, not a log line.

What it contains

  • DecisionRecord, evidence, approval, audit, undo
  • Proposal lifecycle
  • Hash/fingerprint and verification

What it touches

  • Runtime and execution
  • Host audit and export
  • Decision outcomes and replay

Why it matters

The lifecycle is explicit: draft → approved → executed → undone or rejected. A record that cannot be verified is not evidence.

laix/appkit/records/“The decision record is the product’s memory of accountability.”
Integration / Records10
Records are storage-free in LAIX; the host persists them. The record includes evidence, approval, audit and undo. Proposal is the lighter lifecycle for a suggested change.
Integration 04 / 07Delivery

App kit · integration

Delivery

Show it, send it or hold it. Delivery is a port, not a channel; the host owns the notification or UI transport.

What it contains

  • DeliveryPort and DeliveryReceipt
  • NullDelivery for silent or test runs
  • Delivery outcome and acknowledgement

What it touches

  • Layer decisions with deliver
  • Host channels: chat, email, UI, voice
  • Attention and quiet hours

Why it matters

A decision is not a delivery. LAIX can decide to guide now; the host decides which channel and whether it actually reaches the user.

laix/appkit/delivery.py“The decision says whether to deliver. The host owns how.”
Integration / Delivery11
Delivery is deliberately small. LAIX does not own email, chat or the UI. The host implements the port and reports a receipt. This is where notification policy meets the actual channel.
Integration 05 / 07Platform

App kit · integration

Platform

The execution seam below LAIX: run a skill, cancel it, ask for approval, read state and return events.

What it contains

  • Platform and InMemoryPlatform
  • SkillCall, ApprovalRequest, Event
  • Capability levels: fast, balanced, deep

What it touches

  • Execution bridge and runtime
  • Host workers, tools and approvals
  • Trace and receipt events

Why it matters

The host can wrap openJiuwen, a cloud runtime or its own worker. LAIX does not need to know which.

laix/appkit/platform.py“Platform is where the decision becomes work.”
Integration / Platform12
Platform is a contract, not an implementation. run_skill, cancel, request_approval, read_state, write_state, events, capability. A real platform wraps the host’s worker or openJiuwen. LAIX never imports it.
Integration 06 / 07Live Context

App kit · integration

Live Context

The perception loop. Cheap detectors run on every event; deep detectors run only when uncertainty, gain, cost and latency justify them.

What it contains

  • LiveContext and CallableDetector
  • PerceptionEvent and PerceptionFrame
  • Allowed, skipped, remaining uncertainty and cost

What it touches

  • Perception events and resource budgets
  • Host detectors and events
  • Decision situations built from frames

Why it matters

The host sees. LAIX decides what is worth running and records what it skipped. That is how perception stays affordable.

laix/appkit/live_context.py“Cheap always. Deep only when it pays for itself.”
Integration / Live Context13
Live Context is a loop, not a model. The host drives events. Cheap detectors run always. Deep detectors clear a budget. The frame is the audit of what was skipped. This is the natural next step for StudyRoom’s camera and STT.
Integration 07 / 07Bench

App kit · integration

Bench

The regression net. Ten suites, twenty-five cases, Python and TypeScript. A policy change without a case is a guess.

What it contains

  • run_bench() and case suites
  • Agreement, failures and JSON output
  • Same cases in Python and TypeScript

What it touches

  • Every decision class
  • Evaluation and shared fixtures
  • CI and release gates

Why it matters

It catches drift across policies and languages. Add a case before changing behaviour, not after a regression.

laix/appkit/bench.py“Bench is the contract’s regression net.”
Integration / Bench14
Ten suites, twenty-five cases. The bench compares verb, reason_code, action_id and requires_approval. It is deterministic and local. Add a case whenever a policy changes. The same fixtures should exist in both languages.
Definition 01 / 02Contracts

Core · definition

Contracts

Agreed data shapes, not one-way inputs. Request, response and record all use the same vocabulary: what is happening, what can be done, what was chosen, and what happened.

What it contains

  • Request: Situation, Action, Belief, Constraint, Goal, Observation
  • Response: Decision
  • Record: Outcome, Receipt, Trace
  • Shared enums: verbs, phases, horizons, outcome labels

What it touches

  • Every other component uses these records
  • The host and the JSON schema
  • Python and TypeScript packages

Why it matters

Contracts are shared shapes. The request uses some, the decision uses one, the record uses the rest. If the vocabulary changes, every component changes together.

laix/core/contracts.py"The vocabulary underneath everything you just saw. A decision layer is only as stable as its contracts."
Definition / Contracts15
The ten core records are the shared vocabulary. They carry no app-specific names. This is the last definition slide because every earlier component already used these nouns.
Definition 02 / 02Schema

Core · definition

Schema

The contracts as machine-readable JSON. Versioned, shared and used to catch drift between Python, TypeScript and the host.

What it contains

  • Generated JSON schema
  • SCHEMA_VERSION and shared contract names
  • Validation-friendly record shapes

What it touches

  • Python and TypeScript packages
  • Hosts and exports
  • Release and compatibility checks

Why it matters

A contract that cannot be validated is a suggestion. Schema versioning is how a host knows what it is integrating with.

laix/core/schema.py · schemas/“The schema is the contract’s executable form.”
Definition / Schema16
This is tooling, not a runtime service. It keeps the contract honest across languages and releases. The generated schema is not a separate decision engine.
